### A. Termux 通道（建议最先，独立无依赖）
机制（已联网核实）：向 `com.termux/com.termux.app.RunCommandService` 发 RUN_COMMAND intent。
- 前置：主应用声明 `<uses-permission android:name="com.termux.permission.RUN_COMMAND"/>`（危险权限，用户在 Termux 应用信息→附加权限授予）+ `<queries><package android:name="com.termux"/></queries>`；Termux 侧 `~/.termux/termux.properties` 需 `allow-external-apps = true`；Android≥10 需给 Termux“关联应用”权限
- 执行：`RUN_COMMAND_PATH=/data/data/com.termux/files/usr/bin/bash` + `RUN_COMMAND_ARGUMENTS=["-c", cmd]` + `RUN_COMMAND_RUNNER="app-shell"` + `WORKDIR`；结果经 `RUN_COMMAND_PENDING_INTENT`（broadcast）回传 stdout/stderr/exitCode

## 3.8 记忆系统归档缺陷修复（2026-09-27 深夜，用户报“不保留上次整理的记忆”）

**根因（实锤）**：`FactDb.archiveUnknownVersionDatabase` 的版本守卫写死 `if (version <= 13) return`，
而数据库已升到 **v14**（MIGRATION_13_14）——v14 真库被误判为“未知高版本”，**每次启动被归
档重建为空库**；且归档时不 checkpoint 就把 -wal 删掉，连备份都基本是空的（MuMu 旧数据里的
83 个 `.pre-destructive.bak.N` 全是 4KB 空库）。叠加因素：`MemoryLegacyReset` 的提示机制写入
后从未被 app 层消费 → 用户全程无任何提示。症状链：会话内写入正常（日志“吸收 9 条/投影 13 条”）
→ 下次启动清零（“事实记忆流/原事实 0”）→ 表现为“不保留上次整理的记忆”。

**修复**：
- 守卫改为引用 `FACT_DB_VERSION` 常量（与 @Database 版本、迁移链末端三处同源）；
- 归档保真：归档前 `wal_checkpoint(TRUNCATE)`，打不开/失败时把 -wal/-shm 随备份改名保留；
- 一次性数据救援：仅在「有未消费归档标记 + 主库缺失或空 + 存在非空且版本可迁移的备份」
  时迁回（每库只尝试一次；迁回前把当前空库另存为 `.replaced-by-recovery.bak`）；
- 记忆页提示接线：恢复成功 → «已从版本变更归档中恢复 N 条记忆»；仅有归档事件 → «曾因版本变更归档重建»（i18n×7）。
- UI：长记忆点击展开（标题/正文点按或“展开/收起”，阈值 ≥80 字或含换行）。

**验证**：FactDbLegacyResetTest 扩到 7 用例（v14 重开不清空回归 / v15 归档 / 误归档恢复 /
无标记不恢复 / v1-v2 归档 / v11 不归档）；MuMu 上将做制造备份的恢复演练。
**给用户的实话**：手机上若恰好有“非空备份”可被自动找回；空备份无法恢复（历史 WAL 已被删）——
MuMu 实测的备份全为空。今后不再丢。
